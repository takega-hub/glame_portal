# GLAME: агент контроля фотоотчётов по мерчендайзингу

Дата подготовки: 2026-06-01

## Цель

Подключить к GLAME Platform агента, который контролирует внутренние фотоотчёты магазинов:

1. Проверяет, что фотоотчёт загружен за нужную дату и по нужным магазинам.
2. Проверяет полноту отчёта по распоряжению: зал, витрины, центральный стол/остров, брендовые зоны, каменные кубы, касса/упаковка, запас/шкафы/отложка.
3. Оценивает качество мерчендайзинга по текущей концепции GLAME: выкладка по брендам, внутри бренда категории/акценты/воздух/комплекты.
4. Видит фактическое наличие на витрине по фотоотчёту и фиксирует распознанные/предположительные изделия.
5. Сопоставляет видимые изделия с карточками 1С/каталога по внешним параметрам и фото товара.
6. Формирует сводку для администратора: статус отчёта, замечания, что переделать, риски по витринам/запасу, подозрения на несоответствие витрина ↔ 1С.

## Важные правила

- ТРК Меганом не анализируем по умолчанию.
- Основные магазины: ТРК Центрум; Ялта, Набережная Ленина, 18.
- Фотоотчёты внутренние: запас, шкафы, упаковка, отложка допустимы и должны проверяться как зоны внутреннего контроля.
- Выкладка сейчас строится по брендам. Категории проверяются внутри брендовых зон, а не вместо брендовой логики.
- Нельзя автоматически утверждать отчёт без визуальной проверки.

## MVP-архитектура

### 1. Источник фотоотчётов

`MerchPhotoReportSourceService`

Функции:
- читать публичную папку Яндекс.Диска через Cloud API `/v1/disk/public/resources`;
- обходить дерево папок;
- нормализовать магазины и даты;
- считать количество фото;
- определять, какие отчёты есть за сегодня;
- фиксировать отсутствующие отчёты.

Конфиг:
- `MERCH_PHOTO_REPORT_PUBLIC_URL`
- `MERCH_PHOTO_REPORT_SKIP_STORES=Меганом,Метаном`
- `MERCH_PHOTO_REPORT_REQUIRED_STORES=ТРК Центрум;Ялта, Набережная Ленина, 18`

### 3. Анализ полноты отчёта

`MerchPhotoReportChecklistService`

Проверяет наличие обязательных зон:
- фасад/вход;
- общий вид зала;
- центральный стол/остров;
- витрины/настенные зоны;
- брендовые зоны крупно;
- каменные кубы/подиумы;
- касса;
- упаковка;
- запас/шкафы;
- отложка, если есть.

На первом этапе зона определяется LLM-vision классификацией кадра. Позже можно обучить/кэшировать классификатор.

### 4. Агент мерчендайзинга

Выход JSON:

- upload_status
- good_points

- admin_summary_text

### 5. Сопоставление с 1С/каталогом

MVP не должен обещать 100% распознавание изделия по фото витрины: украшения мелкие, бликуют, лежат под углом. Нужна вероятностная логика.

Этапы:
1. Из платформы уже доступны продукты `/api/products/paged` с полями: `id`, `name`, `article`, `external_id`, `brand`, `category`, `images`, `stock`.
2. Для каждого товара с фото строим визуальные embeddings по карточке 1С/каталога.
3. Для каждого кадра витрины выделяем регионы с украшениями.
4. Считаем embeddings по регионам и ищем ближайшие товары среди того же бренда/категории/остатков магазина.
5. Возвращаем не “точно найдено”, а уровни:
   - `matched` — высокая уверенность;
   - `possible_match` — похоже, но нужна проверка;
   - `no_match` — на витрине есть изделие, но нет уверенного товара в каталоге;
   - `needs_human_review` — кадр/блик/мелкий товар мешает проверке.

Важно: 1С-остатки по магазинам должны быть доступны не только суммарным `stock`, но и по store_id/store_name. Если текущий endpoint отдаёт только общий stock, нужен отдельный источник остатков по магазину.

### 6. API endpoints

Новые read-only endpoints:

- `GET /api/merch-photo-reports/reports?date=YYYY-MM-DD`
- `GET /api/merch-photo-reports/reports/{report_id}`
- `POST /api/merch-photo-reports/check-uploads?date=YYYY-MM-DD`
- `POST /api/merch-photo-reports/analyze?date=YYYY-MM-DD&store_name=...`
- `GET /api/merch-photo-reports/summary?date=YYYY-MM-DD`

Write endpoints меняют только внутренние результаты анализа, не 1С и не товары.

### 7. UI

Раздел в админке: `Мерчендайзинг → Фотоотчёты`

Экран:
- дата;
- магазин;
- статус заливки;
- статус анализа;
- количество фото;
- чек-лист зон;
- контакт-лист с номерами кадров;
- замечания по кадрам;
- блок “что переделать”;
- блок “возможные изделия на витрине / сопоставление с 1С”.

### 8. Ежедневный контроль

Cron:
- 12:30 — проверить заливку отчётов за сегодня;
- 13:00 — если отчёт есть, запустить анализ;
- 13:15 — отправить сводку администратору;
- 17:00 — повторная проверка отсутствующих/переделанных отчётов.

### 9. Интеграция с текущим кодом

Обнаружено:
- API health работает.
- OpenAPI доступен.
- Уже есть продукты `/api/products/paged` с фото товара.
- Есть inventory module `/api/inventory/*` и `InventoryControlService`.
- Есть существующий `photo_analysis_orchestrator.py`, но он относится к анализу портретов/стилиста, его нельзя напрямую использовать для витрин.
- Есть `inventory_merchandising_agent.py`, который даёт товарные рекомендации по остаткам/продажам, но не анализирует фотоотчёты.

Рекомендуется создать отдельный домен:
- `backend/app/api/merch_photo_reports.py`
- `backend/app/services/merch_photo_report_source_service.py`
- `backend/app/services/merch_photo_report_analysis_service.py`
- `backend/app/agents/merch_photo_report_agent.py`
- `backend/app/models/merch_photo_report.py`

## MVP-порядок реализации

1. Read-only Yandex Disk scanner + API `check-uploads`.
2. Сохранение отчётов/фото/статуса в БД.
3. Генерация контакт-листов и LLM-vision анализ по правилам GLAME.
4. Админская сводка по качеству и замечаниям.
5. UI раздел фотоотчётов.
6. Сопоставление с каталогом/1С по фото товара и внешним параметрам.
7. Автоматические ежедневные уведомления.

## Риски

- Распознавание конкретных украшений на витрине по общим фото будет вероятностным, не бухгалтерски точным.
- Для точного сопоставления нужны хорошие карточные фото в 1С/каталоге и доступ к остаткам по конкретному магазину.
- Нужно не смешивать публичный эстетический контроль и внутренний контроль: служебные зоны допустимы, но должны быть организованы.
- Нужны права/настройки для хранения кеша фото и результатов анализа.

## Решение по запуску

Безопасный первый шаг: реализовать read-only MVP — сканер заливки + анализ качества/полноты + сводка. Сопоставление витрины с 1С добавить вторым этапом после проверки качества товарных фото и доступности остатков по магазинам.
