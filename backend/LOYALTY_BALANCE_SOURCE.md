# Источник данных для бонусных баллов

## Источник истины

Текущий доступный остаток бонусных баллов берем из регистра движений 1С:

```text
AccumulationRegister_БонусныеБаллы_RecordType
```

Карточка `Catalog_ДисконтныеКарты` через OData не содержит поля остатка бонусов. Число, которое видно на форме карты в 1С как `Остаток бонусов`, является отображением формы/конфигурации 1С и не должно использоваться платформой как источник истины.

## Семантика полей регистра

- `Period` - дата движения.
- `RecordType` - тип движения: `Receipt` или `Expense`.
- `Начислено` - сумма начисления в строке движения.
- `КСписанию` - сумма движения по ресурсу "к списанию", а не всегда готовый баланс.
- `БонуснаяКарта_Key` - ID бонусной карты.
- `Recorder` - документ-регистратор.
- `Active` - признак активного движения.

## Расчет текущего доступного остатка

Для текущего остатка учитываем только активные строки с `Period <= now`.

```python
balance = 0
for record in records:
    if record["RecordType"] == "Expense":
        balance -= record["КСписанию"]
    else:
        balance += record["Начислено"]
```

Иными словами:

- начисление `Receipt` добавляет `Начислено`;
- списание `Expense` уменьшает баланс на `КСписанию`;
- корректировка с отрицательным `КСписанию` увеличивает баланс обратно;
- будущие строки по сроку сгорания не считаются текущим доступным остатком.

## OData-вывод по списанию

В `Document_НачислениеСписаниеБонусныхБаллов_СписанияБонусов` через OData доступны только:

- `БонуснаяКарта_Key`;
- `Количество`;
- `КорректировкаКСписанию`.

Полей лота, даты первоначального начисления или даты сгорания в табличной части нет. Поэтому текущий технический документ `Баллы -> GLM` пишет одну строку расхода в `AccumulationRegister_БонусныеБаллы_RecordType`, но не уменьшает регистр начисленных лотов:

```text
AccumulationRegister_НачисленияБонусныхБаллов_RecordType
```

Реальные списания бонусов из РМК/чека в 1С регистрируются иначе: `Document_ЧекККМ` содержит строку `БезналичнаяОплата` с `ВидОплаты = "Бонусы"`, `БонуснаяКарта_Key` и `СуммаБонусов`. После проведения такой чек распределяет расход по срокам/лотам: появляются движения `Expense` по `Начислено` и отдельные будущие движения по `КСписанию` с `ДатаПервоначальногоНачисления`.

Дополнительный OData-spike показал рабочий путь без чека ККМ: `Баллы -> GLM` можно проводить как отрицательное ручное начисление в той же табличной части, которую используем для обычного начисления:

```text
Document_НачислениеСписаниеБонусныхБаллов
  НачисленияБонусов:
    Количество = -points
    ДатаНачисления = now
    ДатаСгорания = now + срок действия программы
  СписанияБонусов = []
```

Тест `-10` баллов через OData дал ожидаемый результат:

- рабочий остаток: `400 -> 390`;
- начисленные лоты: `750 -> 740`;
- после `Unpost` тестового документа остатки вернулись `400 / 750`.

Итог: для `Баллы -> GLM` используем отрицательное начисление, а не строку `СписанияБонусов`. Чек ККМ остается только для реальной покупки в магазине.

Для старых документов, уже проведенных через `СписанияБонусов`, был протестирован отдельный repair-путь:

```text
Document_НачислениеСписаниеБонусныхБаллов
  НачисленияБонусов:
    Количество = -delta_lots
  СписанияБонусов:
    Количество = 0
    КорректировкаКСписанию = -delta_lots
```

Он уменьшает визуальные начисленные лоты, но сохраняет рабочий доступный остаток `К списанию`. После теста этот путь отключен по умолчанию через `GLM_LOYALTY_LOT_REPAIR_ENABLED=false`, потому что автоматическая правка лотов по OData-расхождению может не совпасть с тем, как форму карты пересчитывает 1C.

## Важное правило для CryptoGLAME

Операции `Баллы -> GLM` и `GLM -> баллы` должны опираться на расчетный остаток по регистру движений, а не на визуальное поле формы карты. Это защищает от повторного использования уже списанных баллов.
