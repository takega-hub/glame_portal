# План внедрения реферальной программы GLAME

Дата анализа: 2026-06-26

## 1. Цель

Внедрить реферальную программу, в которой:

- покупатель, стилист, блогер или внешний партнер может подключиться к партнерской программе;
- система выдает уникальный реферальный код;
- новый покупатель вводит код при первой покупке в магазине или в приложении;
- рефералу начисляется бонус за первую покупку;
- партнеру начисляется комиссия с каждой подтвержденной покупки этого покупателя;
- все ключевые события отражаются в 1С;
- у партнера есть личный кабинет со статистикой регистраций, покупок рефералов, начислений, удержаний и выплат.
- официальный контакт партнерской программы: `partner@glamejewelry.ru`.

## 2. Что уже есть в платформе

По текущему коду платформа уже имеет большую часть инфраструктуры, на которую можно опереться.

### Backend

- Пользователи и покупатели хранятся в `users`: телефон, карта 1С, `customer_id_1c`, `discount_card_id_1c`, баллы, метрики покупок.
- Онлайн-заказ создается через `POST /checkout`; данные заказа лежат в `orders`, товары в `order_items`, платежи в `payments`.
- История офлайн/1С-покупок импортируется в `purchase_history` с `document_id_1c`, `store_id_1c`, товаром, суммой и датой покупки.
- Бонусная программа уже реализована через `LoyaltyService` и таблицу `loyalty_transactions`.
- Заказы из приложения/сайта выгружаются в 1С через CommerceML XML: `/1c/orders/export.xml`, `/1c/exchange`, `static/1c_exchange/orders.xml`.
- Покупатели, история покупок и лояльность синхронизируются с 1С через OData.

### Клиентские приложения

- Веб-кабинет покупателя уже есть: `/customer`, `/customer/loyalty`, `/customer/purchases`.
- Мобильное приложение Flutter уже имеет `cart`, `checkout`, `customer_cabinet`, `loyalty`.
- В checkout уже передаются `contact`, `delivery`, `discount_amount`, `use_bonus_points`, `meta`. Это удобная точка для добавления `referral_code`.

### Вывод

Реферальную программу не нужно строить как отдельную внешнюю систему. Оптимально добавить новый backend-домен `referrals`, который связывает пользователей, коды, покупки из `orders` и `purchase_history`, бонусные транзакции и 1С-обмен.

## 3. Предлагаемая бизнес-логика MVP

### Участники

- **Партнер**: пользователь, который зарегистрировался в реферальной программе и получил код.
- **Реферал**: новый покупатель, который применил код при первой покупке.
- **Администратор**: сотрудник GLAME, который управляет ставками, статусами, выплатами и спорными ситуациями.

### Правила применения кода

1. Код можно применить только к первой покупке покупателя.
2. Первая покупка может быть:
   - онлайн-заказом из приложения/сайта;
   - офлайн-покупкой в магазине, если код был введен кассиром/менеджером в 1С или в админке платформы.
3. Нельзя применить собственный код.
4. Код должен быть активным.
5. Один покупатель может быть закреплен только за одним партнером.
6. Реферальная связь становится активной после оплаты/подтверждения первой покупки.

### Бонус рефералу

По оферте GLAME рекомендованный клиент получает `1000` бонусов GLAME на первую покупку от `7000` рублей. Бонус действует `7` календарных дней с момента первого контакта/активации кода, может покрывать не более `30%` покупки и применяется только если клиент указал код до покупки.

Почему не скидка сразу в MVP:

- бонусы уже есть в `loyalty_transactions`;
- проще отразить в 1С как операцию лояльности;
- меньше рисков с оплатой, возвратами и фискальными скидками.

### Вознаграждение партнеру

В программе должно быть два режима вознаграждения партнера. При регистрации всегда подключается режим `Баллы GLAME`; выбор режима на этапе регистрации не показывается. Денежное агентское вознаграждение становится доступно только после достижения заданного уровня партнера и прохождения оформления договора.

При первичной регистрации партнера платформа хранит профиль в своей БД и создает в 1С обычного покупателя для начисления бонусных баллов. Для этого обязательны ФИО и телефон. Покупатель в 1С создается в отдельной группе контрагентов `Покупатели / Партнер-рефовод`, чтобы партнеры не смешивались с основным сегментом покупателей в операционном учете.

#### Режим 1. Баллы GLAME

Партнер получает вознаграждение баллами внутри системы GLAME.

Особенности:

- агентский договор не нужен;
- паспортные данные не запрашиваются;
- агентский контрагент/договор 1С для партнера не создается;
- в 1С создается покупатель в группе `Партнер-рефовод`, чтобы на его бонусную карту начислять баллы;
- начисление проходит через `loyalty_transactions` на пользователя-партнера;
- баллы можно использовать по правилам бонусной программы GLAME;
- в личном кабинете показывать баланс баллов, историю начислений и покупки, за которые начислены баллы.

#### Режим 2. Денежное агентское вознаграждение

Партнер получает денежную комиссию как агент.

Обязательные условия:

- партнер достиг уровня, который открывает переход на денежное вознаграждение;
- партнер должен быть ИП или самозанятым;
- партнер предоставляет паспортные данные и реквизиты, необходимые для агентского договора;
- партнер подтверждает, что самостоятельно платит налоги и несет ответственность за свой налоговый режим;
- платформа создает или связывает контрагента в 1С для агентского учета, отдельно от покупательской записи, используемой для баллов;
- в 1С создается агентский договор;
- комиссии оформляются как агентские начисления по договору.

Ставка вознаграждения зависит от уровня партнера по годовому реферальному обороту:

| Уровень | Годовой реферальный оборот | Ставка |
|---|---:|---:|
| Stylish Start / Стильный старт | до 50 000 ₽ включительно | 3% |
| Stylish Pro / Стильный профи | 50 001-150 000 ₽ включительно | 5% |
| Stylish Expert / Стильный эксперт | 150 001-300 000 ₽ включительно | 7% |
| Stylish Privé / Стильный привилегированный | от 300 001 ₽ | 10% |

Переход на денежное вознаграждение открывается с уровня `Stylish Pro`. Новая ставка применяется к последующим подтвержденным покупкам, а не к покупке, которой партнер пересек порог уровня.

Расчетная база:

```text
commission_base = purchase_goods_amount - discounts - returns
commission_amount = floor(commission_base * commission_rate)
```

Для онлайн-заказов базой может быть `orders.subtotal_amount - orders.discount_amount`, без `delivery_amount`.

Для офлайн-покупок базой может быть сумма строк `purchase_history.total_amount` по одному `document_id_1c`, с учетом будущих возвратов, если они доступны в 1С.

Для режима баллов формула может использовать ту же базу, но результат конвертируется в баллы по отдельному правилу, например `1 рубль расчетного вознаграждения = 1 балл`, либо по фиксированному проценту в баллах. Конкретный курс должен быть настройкой программы.

### Статусы комиссии

- `pending` - покупка найдена, комиссия рассчитана, но ждет окна возврата.
- `approved` - комиссия подтверждена и доступна к выплате.
- `paid` - комиссия выплачена.
- `canceled` - покупка отменена или полностью возвращена.
- `adjusted` - сумма изменена из-за частичного возврата/коррекции.

Окно холда по оферте: минимум `30` календарных дней после доставки/передачи товара и при отсутствии отмены, возврата, претензии или признаков злоупотребления.

## 4. Отражение в 1С

Есть два рабочих варианта. Для GLAME лучше начинать с гибридного подхода.

### Вариант A. GLAME как источник реферальной логики, 1С как учет и сверка

Платформа хранит реферальные связи, рассчитывает комиссии, начисляет бонусы и передает в 1С:

- реферальный код в реквизит заказа;
- ID партнера;
- сумму реферальной комиссии;
- бонус реферала;
- статус начисления/выплаты.

Плюсы:

- быстрее внедрить;
- меньше доработок 1С;
- можно использовать существующие `orders.xml`, OData sync и `loyalty_transactions`.

Минусы:

- для полного учета в 1С нужно договориться о дополнительных реквизитах/документах.

### Вариант B. 1С как источник реферальной логики

1С хранит коды, связи и комиссии, а платформа только показывает данные.

Плюсы:

- учет полностью внутри 1С.

Минусы:

- дороже и дольше;
- понадобится доработка конфигурации 1С УНФ;
- сложнее быстро менять механику программы.

### Рекомендуемый вариант

MVP: Вариант A с двумя учетными ветками:

1. Баллы GLAME: начисления остаются внутри платформы в `loyalty_transactions`.
2. Денежное вознаграждение: полноценная учетная связка в 1С.

Для денежного режима:

- при одобрении партнера платформа создает или связывает контрагента в 1С;
- для партнера создается агентский договор в 1С;
- комиссии оформляются как агентские начисления по договору;
- платформа хранит ID контрагента, ID договора и ID документов начислений 1С;
- личный кабинет показывает не только сумму комиссии, но и учетный статус: контрагент создан, договор активен, начисление передано в 1С, начисление оплачено.

Такой вариант лучше, чем CSV-отчет как основной сценарий для денежных выплат: он сразу дает управляемый учет агентских обязательств, меньше ручной сверки и прозрачнее для выплат. Для балльного режима 1С-контрагент и агентский договор не требуются.

### Что передавать в 1С

#### В заказе CommerceML

Добавить в `OneCOrderXMLService` реквизиты:

- `РеферальныйКод`
- `ПартнерID`
- `ПартнерТелефон`
- `РеферальнаяСвязьID`
- `РеферальныйБонус`
- `РеферальнаяКомиссияОжидаемая`

Эти значения можно брать из `orders.meta.referral`.

#### В покупателе

При создании/обновлении покупателя в 1С передавать:

- `ИсточникРегистрации = referral`
- `РеферальныйКод`
- `Партнер`
- `ДатаПривязки`

Если 1С не принимает кастомные поля через стандартный OData-объект, хранить эти поля в комментарии/дополнительных реквизитах 1С или отдельном регистре.

#### Для бонусов

В платформе бонус рефералу должен создаваться как `loyalty_transactions`:

- `transaction_type = earn`
- `reason = referral_first_purchase`
- `source = referral`
- `source_id = referral_reward_id`

Для 1С нужен один из вариантов:

- синхронизация бонусных операций через существующий механизм лояльности;
- создание документа/операции начисления бонусов в 1С;
- временно: выгрузка отчета начислений для ручной загрузки в 1С.

#### Для комиссий

Для партнера нужно разделять два типа начислений:

- `points` - внутреннее начисление баллов GLAME;
- `cash` - денежное агентское вознаграждение по договору.

В режиме `points` комиссия не является денежным обязательством. Она отражается как начисление баллов на баланс партнера.

В режиме `cash` комиссия не является бонусом покупателя. Это агентское вознаграждение по договору.

Учетная модель:

- в платформе: таблица комиссий, балльных начислений, денежных начислений и выплат;
- для `points`: транзакции в `loyalty_transactions` с `reason = referral_referrer_reward`;
- для `cash`: в 1С контрагент-партнер, агентский договор, документы агентских начислений, оплата/закрытие начислений;
- ключевая связь: `referral_program_members.onec_counterparty_id` + `referral_program_members.onec_agency_contract_id`;
- каждое подтвержденное начисление должно получить `onec_accrual_document_id` или статус ошибки выгрузки.

Передавать в 1С для агентского начисления:

- период;
- контрагент 1С;
- агентский договор;
- партнер в платформе;
- количество покупок;
- база комиссии;
- сумма комиссии;
- ставка комиссии;
- ссылки на документы продаж.

Статусы агентского начисления:

- `approved` - подтверждено в платформе, готово к созданию начисления;
- `exporting_to_1c` - идет передача в 1С;
- `accrued_in_1c` - начисление создано в 1С;
- `export_failed` - ошибка создания начисления;
- `paid` - выплачено/закрыто в 1С;
- `canceled` - отменено или сторнировано.

В `cart_checkout.py`:

1. Добавить `referral_code` в `CheckoutRequest`.
2. До создания заказа вызвать `ReferralService.validate_code`.
3. Если код валиден, создать `referral_attributions` в статусе `pending`.
4. Сохранить реферальные данные в `order.meta`.
5. После успешной оплаты/создания COD-заказа:
   - если это первая покупка пользователя, активировать связь;
   - начислить бонус рефералу через `LoyaltyService.earn_points`;
   - создать `referral_commissions` в статусе `pending`;
   - обновить `orders.xml`.
6. Для YooKassa нужно также обработать webhook оплаты: если сейчас комиссия создается до фактической оплаты, она должна быть `pending` до статуса `succeeded`.

## 8. Интеграция с офлайн-магазинами и 1С

### Ввод кода в магазине

Возможные сценарии:

1. Кассир вводит код в 1С в дополнительный реквизит продажи/чека.
2. Кассир вводит код в админке GLAME, привязывая его к телефону покупателя.
3. Покупатель заранее вводит код в приложении, а офлайн-покупка позже подтягивается из 1С по телефону/карте.

Для MVP лучше поддержать сценарии 2 и 3, а затем доработать 1С для сценария 1.

### Обработка покупок из `purchase_history`

После синхронизации покупок из 1С добавить задачу:

```text
ReferralCommissionSyncJob
```

Алгоритм:

1. Найти новые документы `purchase_history.document_id_1c`.
2. Сгруппировать строки по документу.
3. Определить покупателя `user_id`.
4. Проверить, есть ли активная `referral_attribution`.
5. Если это первая покупка после ввода кода, активировать связь и начислить бонус.
6. Для каждой подтвержденной покупки создать/обновить `referral_commissions`.
7. Не создавать дубликаты по `document_id_1c`.

### Доработки 1С

Нужно согласовать с 1С-специалистом:

- где хранить реферальный код в чеке/реализации;
- можно ли добавить дополнительные реквизиты к заказу/продаже;
- как создавать/хранить начисления бонусов;
- как оформлять комиссию партнера: документ начисления, взаиморасчеты, отчет для бухгалтера;
- как отражать возвраты и сторнировать комиссии.

## 11. Антифрод и ограничения

Обязательные проверки:

- запрет собственного кода;
- один активный партнер на одного покупателя;
- код только на первую покупку;
- телефон покупателя должен быть уникальным;
- ограничение количества рефералов с одного устройства/IP можно добавить позже;
- ручная блокировка партнера;
- пересчет комиссий при возврате;
- холд комиссии до окончания периода возврата;
- аудит всех ручных изменений.

### Юридические и персональные данные для денежного режима

Для режима `cash` нужно добавить отдельный KYC-flow.

Обязательные данные:

- ФИО;
- телефон;
- email;
- юридический статус: ИП или самозанятый;
- ИНН;
- паспортные данные, необходимые для агентского договора;
- платежные реквизиты;
- подтверждение согласия с правилами программы;
- подтверждение, что партнер самостоятельно платит налоги и отвечает за корректность своего налогового режима.

Ограничения:

- денежные выплаты недоступны, пока `passport_data_status != verified`;
- денежные выплаты недоступны, пока `legal_status` не `self_employed` или `individual_entrepreneur`;
- денежные выплаты недоступны, пока `tax_responsibility_confirmed_at` пустой;
- денежные выплаты недоступны, пока `onec_agency_contract_status != active`;
- паспортные данные не показывать в личном кабинете после отправки полностью: только статус проверки и маскированные фрагменты, если нужно;
- доступ к паспортным данным только для админов с отдельным правом;
- хранение паспортных данных должно быть защищенным: шифрование на уровне приложения/БД или отдельное защищенное хранилище, аудит доступа.

Рекомендации:

- не выплачивать комиссию по полностью оплаченным бонусами заказам;
- не начислять комиссию с доставки;
- не начислять комиссию с отмененных заказов;
- по частичным возвратам уменьшать комиссию пропорционально возвращенной сумме;
- не показывать партнеру персональные данные реферала полностью: маскировать телефон/ФИО.

## 14. Риски

| Риск | Вероятность | Влияние | Что делать |
|---|---:|---:|---|
| Ошибка создания контрагента или агентского договора в 1С | средняя | высокое | показывать статус ошибки, не разрешать выплаты до активного договора |
| Дубли покупок из 1С | средняя | высокое | idempotency по `document_id_1c` |
| Возвраты не синхронизируются | средняя | высокое | держать комиссию в `pending`, ручная сверка на MVP |
| Саморефералы и злоупотребления | высокая | среднее | запреты, холд, админ-блокировка |
| Не хватает данных партнера для договора | средняя | высокое | собирать обязательные поля до создания договора, показывать статус в кабинете |
| Расхождение бонусов платформы и 1С | средняя | высокое | один источник истины для бонусного баланса или регулярная сверка |

## 16. Оценка сроков

Ориентировочно:

- MVP без глубокой доработки 1С: 3-4 недели.
- Полная версия с доработками 1С, выплатами и возвратами: 5-8 недель.

Команда:

- backend: 1 разработчик;
- frontend/mobile: 1 разработчик;
- 1С-специалист: частичная занятость;
- QA/аналитик: частичная занятость;
- бизнес-владелец программы: для правил, ставок и спорных сценариев.
