# GLAME APP — Обновленная спецификация блока и сценария «Подбор по фото»

**Версия:** 3.0  
**Дата обновления:** 2026-05-07  
**Раздел:** Главная страница → Блок 3 → Сценарий «Подбор по фото»  
**Назначение документа:** единая спецификация для UX/UI, frontend, backend, AI-логики и контент-команды.

---

## 1. Статус решения

Фиксируем окончательно:

- **3-й блок Главной страницы посвящен только одной функции — подбору по фото.**
- В этом блоке **не показываются** другие сценарии подбора: подарок, к образу, размер, на событие и т.д.
- Эти сценарии могут существовать ниже на Главной или в отдельном разделе, **но не в блоке 3**.
- В пользовательском интерфейсе **не раскрываем технические детали анализа**.
- В текстах не пишем, что именно система анализирует на уровне внутренних параметров.
- Задача блока: продать идею сервиса, а не объяснять механику AI.
- **Без регистрации / авторизации пользователь не может загрузить фото и не может запустить сценарий анализа.**

---

## 2. Принцип авторизации в этом сценарии

Фиксируем отдельным правилом:

- просмотр блока 3 на Главной — **доступен всем**;
- просмотр страницы с объяснением сценария и требований к фото — **может быть доступен всем**;
- просмотр подсказки **«Какое фото подойдет?»** — **может быть доступен всем**;
- **выбор фото из галереи, съемка фото, загрузка фото, запуск анализа и получение персонального результата — только для авторизованного пользователя**.

### Почему это решение оптимально

Такой подход:

- снижает барьер входа в сценарий;
- позволяет сначала продать ценность сервиса;
- не тратит разработку на обработку анонимных фото;
- не создает серую зону по хранению персональных изображений для неавторизованных пользователей;
- повышает шанс регистрации, потому что пользователь уже понял, зачем ему этот сценарий.

### Итоговая рекомендация

**Рекомендуемый вариант реализации: мягкий auth gate на действии загрузки фото.**

То есть:

- пользователь может открыть блок;
- может прочитать, как работает сервис;
- может посмотреть, какое фото подойдет;
- но при попытке нажать **«Выбрать или сделать фото»** / **«Загрузить фото»** система проверяет авторизацию;
- если пользователь не авторизован, открывается экран / bottom sheet авторизации;
- после успешной авторизации пользователь возвращается в сценарий и продолжает действие без потери контекста.

## 4. Состав сценария

Сценарий состоит из следующих экранов / состояний:

1. **Блок 3 на Главной** — тизер сервиса.
2. **Страница загрузки фото** — основной вход в сценарий после нажатия CTA.
3. **Bottom sheet «Какое фото подойдет?»** — объясняет требования к фото.
4. **Auth gate / auth wall** — обязательный шаг для неавторизованного пользователя.
5. **System picker** — выбор между камерой и галереей.
6. **Экран проверки фото** — просмотр выбранного фото перед запуском анализа.
7. **Экран анализа** — промежуточное состояние.
8. **Экран результата** — вывод рекомендаций и товаров.

# 5. Экран 1 — Блок 3 на Главной

## 5.1. Роль блока

Блок 3 — это **не отдельная страница загрузки**, а тизер / вход в сервис.

Он должен:

- объяснять ценность функции;
- быть визуально сильным;
- не раскрывать конфиденциальную внутреннюю логику;
- переводить пользователя на отдельную страницу загрузки фото.

## 5.2. Пользовательский текст

### Заголовок
**Подбор по фото**

### Подзаголовок / описание
Рекомендуемый подход к тексту:

> Загрузите фото — и мы поможем подобрать украшения, которые звучат с вашей внешностью естественно, точно и без случайных решений.

или

> Подбор, который начинается с вас. По фото мы соберем украшения под ваш образ, характер внешности и впечатление, которое вы хотите создать.

### Запреты по тексту
В пользовательских текстах **не писать**:

- «анализируем мочку уха»;
- «анализируем морщины»;
- «анализируем растянутость мочки»;
- «анализируем форму лица / цвет глаз / типаж» в прямой технической формулировке;
- любые медицинские, диагностические или слишком техничные формулировки.

## 5.3. CTA блока на Главной

### Primary CTA
**Загрузить фото**

Логика:

```dart
navigateToPhotoUploadPage()
```

### Secondary CTA
**Как это работает** / **Какое фото подойдет?**

Логика:

```dart
openPhotoGuideBottomSheet()
```

> Примечание: если бренд в будущем захочет полностью закрыть этот сценарий для гостей, можно поставить auth gate уже на CTA блока. Но на текущем этапе рекомендован более мягкий вариант: gate не на входе, а на действии загрузки.

# 6. Экран 2 — Страница загрузки фото

## 6.1. Роль экрана

Это **отдельная страница**, на которую пользователь попадает после нажатия CTA из блока 3.

Она нужна затем, чтобы:

- подготовить пользователя к загрузке корректного фото;
- показать пример подходящего снимка;
- сократить количество неподходящих загрузок;
- объединить выбор из галереи и съемку в одном понятном действии.

## 6.2. Ключевое изменение

Фиксируем:

- страница **не должна дублировать** блок 3 с Главной;
- визуально она может быть связана по стилю, но должна решать другую задачу — **подготовку к корректной загрузке**;
- на странице должен быть **явный акцент на ознакомлении с требованиями к фото**;
- желательно подвести пользователя к инструкции **до** открытия выбора файла / камеры.

## 6.3. UX-логика страницы

Рекомендуемый порядок элементов:

```text
Top bar
    ↓
Hero / editorial image или пример подходящего фото
    ↓
Заголовок
    ↓
Короткий вдохновляющий текст
    ↓
Акцентный блок / ссылка «Какое фото подойдет?»
    ↓
Primary CTA: Выбрать или сделать фото
    ↓
Helper text: сервис доступен после входа в профиль
```

## 6.4. Тексты страницы

### Заголовок
Варианты:

- **Подбор по фото**
- **Начнем с фото**
- **Покажите себя**

### Подзаголовок
Варианты безопасной формулировки:

- **Чтобы подбор получился точнее, выберите спокойный портрет с хорошо видимым лицом.**
- **Ориентируйтесь на пример ниже — так результат будет точнее.**
- **Сначала посмотрите, какое фото подойдет для подбора.**

### Дополнительная подпись про доступ
Ненавязчиво, но ясно:

- **Загрузка фото доступна после входа в профиль.**
- **Чтобы сохранить результат и получить персональную подборку, войдите в аккаунт.**

**Выбрать или сделать фото**

### Secondary CTA / link
**Какое фото подойдет?**

### Допустимый UX-паттерн
Если нужно усилить акцент на инструкции, можно использовать:

- текстовую ссылку над CTA;
- инфо-карточку;
- нативный info-row с иконкой;
- небольшую подпись перед CTA: **«Сначала посмотрите пример подходящего фото»**.

# 7. Экран 3 — Bottom sheet «Какое фото подойдет?»

## 7.1. Роль

Bottom sheet нужен не как отдельная страница, а как **короткая, понятная и полезная подсказка**, чтобы не загружали случайные или неподходящие фото.

## 7.2. Когда открывается

Открывается:

- по нажатию **«Какое фото подойдет?»**;
- по нажатию **«Как это работает»**;
- опционально — автоматически при первом входе на страницу загрузки (только если UX-тесты подтвердят, что это не мешает).

## 7.3. Структура bottom sheet

```text
Заголовок
Короткое объяснение
Пример удачного фото
Список коротких правил
Primary CTA: Выбрать или сделать фото
Secondary CTA: Понятно / Закрыть
```

## 7.4. Тексты

### Заголовок
**Какое фото подойдет?**

### Подзаголовок
**Чтобы подбор был точнее, выберите спокойный портрет, где хорошо видно лицо.**

### Правила в интерфейсе
Показывать кратко и дружелюбно:

- Один человек в кадре
- Лицо видно крупно
- Мягкий свет
- Без очков и сильных фильтров
- Открыты уши и шея
- Спокойный ракурс, без сильного наклона

## 7.5. Пример фото

Требования к референсу / примеру в UI:

- женщина из ЦА GLAME;
- возраст визуально ближе к аудитории бренда, не подростковый образ;
- портретный кадр;
- чистый, спокойный, premium look;
- лицо читается крупно;
- без визуального шума.

## 7.6. CTA bottom sheet

### Primary CTA
**Выбрать или сделать фото**

Логика:

**Понятно**


# 8. Экран 4 — Auth gate / auth wall

## 8.1. Роль

Это обязательный экран / bottom sheet для пользователей без авторизации.

Он появляется **до выбора фото**, а не после.

## 8.2. Когда открывается

Открывается в двух точках:

1. по нажатию **«Выбрать или сделать фото»** на странице загрузки;
2. по нажатию **«Выбрать или сделать фото»** в bottom sheet с инструкцией.

## 8.3. Задача экрана

- объяснить, почему нужен вход;
- дать быстрый вход / регистрацию;
- не уводить пользователя из сценария надолго;
- после успеха вернуть пользователя точно в точку действия.

## 8.4. Рекомендуемый текст

### Заголовок
**Войдите, чтобы продолжить**

### Подзаголовок
Варианты:

- **Подбор по фото доступен после входа в профиль. Так мы сможем сохранить результат и собрать персональную подборку именно для вас.**
- **Чтобы загрузить фото и получить персональные рекомендации, войдите или создайте аккаунт.**

## 8.5. CTA auth wall

- **Войти**
- **Создать аккаунт**
- **Продолжить с Apple / Google / по номеру телефона** — в зависимости от выбранной auth-архитектуры
- **Закрыть**

## 8.6. UX-принципы

- лучше использовать **bottom sheet / modal full-screen sheet**, а не жесткий полный редирект без контекста;
- после успешной авторизации **автоматически продолжать прерванное действие**;
- не требовать от пользователя повторно нажимать все заново.

## 8.7. Post-auth continuation

Нужно сохранять `pendingAction`.

Пример:

```dart
enum PendingAction {
  chooseOrTakePhoto,
}
```

При неавторизованном действии:

```dart
pendingAction = PendingAction.chooseOrTakePhoto;
openAuthWall();
```

После успешного входа:

```dart
if (pendingAction == PendingAction.chooseOrTakePhoto) {
  pendingAction = null;
  openSystemPhotoSourcePicker();
}
```

# 10. Экран 6 — Проверка выбранного фото

## 10.1. Назначение

После выбора изображения пользователь попадает на экран проверки.

Задачи экрана:

- показать выбранное фото;
- дать возможность переснять / выбрать другое;
- запустить анализ только после подтверждения.

## 10.2. Элементы

- preview выбранного фото;
- краткий текст подтверждения;
- CTA **Начать подбор** / **Продолжить**;
- secondary CTA **Выбрать другое фото**.

## 10.3. Минимальная валидация

Проверять автоматически:

- лицо обнаружено;
- лицо одно;
- лицо достаточно крупное;
- фото не слишком темное;
- нет сильного размытия;
- фото не обрезано критически.

Если фото не подходит, показать мягкую подсказку:

> На этом фото недостаточно хорошо видно лицо. Попробуйте выбрать более четкий портрет.

# 13. Внутренняя AI-логика (не показывать пользователю)

## 13.1. Внутренние параметры анализа

Этот раздел нужен **только разработчикам / AI-команде / продактам**.

Система может учитывать следующие параметры:

- форма лица;
- пропорции лица;
- общий масштаб внешности;
- визуальная соразмерность черт;
- цветовой характер внешности;
- светлота / контрастность внешности;
- цвет глаз;
- цвет и тон волос;
- визуальная фактурность внешности;
- состояние и видимость мочки уха;
- посадка и читаемость серег;
- зона шеи / ключиц для рекомендаций по подвескам и колье;
- выразительность линий внешности;
- допустимый масштаб украшений;
- уровень фактурности металла / поверхности;
- степень акцентности изделия.

## 13.2. Важное ограничение

Все эти параметры **не должны выводиться в пользовательский интерфейс напрямую**.

В интерфейсе показываем результат в мягкой форме:

- что подходит;
- какой характер украшений лучше смотрится;
- какие изделия рекомендованы.

Не показываем:

- медицинские или оценочные формулировки;
- «мы определили возраст»;
- «мы нашли морщины»;
- «мочка растянута»;
- «дефекты»;
- любые формулировки, которые могут звучать неприятно или небезопасно.

# 14. Логика авторизации и доступа

## 14.1. Уровни доступа

### Неавторизованный пользователь может:

- видеть блок 3;
- открыть страницу загрузки фото;
- прочитать текст сценария;
- открыть инструкцию **«Какое фото подойдет?»**.

### Неавторизованный пользователь не может:

- открыть камеру для сценария подбора;
- открыть галерею для загрузки фото в рамках этого сценария;
- загружать фото на сервер;
- запускать анализ;
- получать персональный результат.

### Авторизованный пользователь может:

- пройти весь сценарий полностью.

## 14.2. Зачем auth нужен именно здесь

Auth нужен для:

- привязки фото к конкретному пользователю;
- сохранения результата подбора;
- возврата к результату позже;
- избранного / сохранения карточек;
- связи с персональной историей клиента;
- корректной работы согласий на обработку данных.

## 14.3. Обязательные технические требования

- фото нельзя отправлять на backend без `userId` / `session` / авторизационного токена;
- все защищенные endpoint'ы сценария работают только под авторизованной сессией;
- если сессия протухла, пользователь должен быть мягко возвращен в auth flow;
- после авторизации нужен возврат в прерванное действие.

# 15. Техническая логика переходов

## 15.1. Routing map

```text
HomeBlock3
  -> PhotoUploadPage
      -> PhotoGuideBottomSheet
      -> AuthWall (if guest & tries upload)
          -> Login / Registration
          -> success -> continue pending action
      -> SystemPhotoSourcePicker
          -> Camera
          -> Gallery
      -> PhotoReviewPage
          -> AnalysisLoadingPage
              -> SelectionResultPage
```

# 16. Рекомендация по реализации auth

## Рекомендуемый вариант (основной)

**Мягкий gate на действии загрузки фото**.

### Плюсы:

- ниже барьер входа;
- пользователь сначала понимает ценность сценария;
- меньше отказов на первом экране;
- логика более премиальная и менее агрессивная;
- удобнее в UX.

### Минусы:

- требуется аккуратное восстановление прерванного действия после входа.

## Альтернативный вариант

**Жесткий gate до входа в сценарий**.

То есть сразу при нажатии CTA из блока 3 открывается auth.

### Плюсы:

- проще разработка;
- жестко защищенный сценарий.

### Минусы:

- хуже конверсия;
- больше ощущение барьера;
- пользователь еще не увидел ценность сценария, но уже должен войти.

## Рекомендуемое решение для GLAME

Для GLAME лучше использовать **первый вариант**:  
**показываем ценность → объясняем, какое фото подойдет → gating только на действии загрузки**.

Это соответствует логике бренда: спокойно, интеллигентно, без лишнего давления.

# 18. Что обязательно учитывать в разработке

## Must-have

- один центральный сценарий;
- страница загрузки отделена от блока на Главной;
- объединенный вход **«Выбрать или сделать фото»**;
- акцент на инструкции по фото;
- **auth gate до загрузки фото**;
- soft validation качества фото;
- скрытие внутренней аналитической логики от пользователя;
- возврат в прерванное действие после входа.

## Must-not

- не раскрывать внутренние параметры анализа в UI;
- не превращать страницу в техно-сканер;
- не дублировать один и тот же экран без новой функции;
- не давать загружать фото гостю;
- не дробить основной сценарий на лишние шаги без UX-смысла.

---

# 19. Итоговое зафиксированное решение

Финально фиксируем следующее:

1. **Блок 3 на Главной** = только вход в сценарий «Подбор по фото».  
2. **После CTA** пользователь попадает на отдельную **страницу загрузки фото**.  
3. На этой странице делаем явный акцент на том, что **сначала желательно ознакомиться с примером подходящего фото**.  
4. Основная кнопка на странице — **«Выбрать или сделать фото»**.  
5. Кнопка **«Какое фото подойдет?»** открывает bottom sheet с примером и короткими правилами.  
6. **Без регистрации / авторизации пользователь не может загрузить фото, открыть системный выбор источника фото и не может запустить анализ.**  
7. При попытке загрузки фото гостем открывается **auth wall**.  
8. После успешной авторизации пользователь **автоматически возвращается в прерванное действие**.  
9. В пользовательских текстах **не раскрываем**, что именно анализируем.  
10. Внутренние параметры анализа остаются **только во внутренней логике / документации для разработки**.  
11. Визуальный стиль и структура должны оставаться в логике GLAME: чисто, спокойно, премиально, без лишних элементов.
